# Shotviva 协作规则（Claude × Codex）

> v2 · 2026-11-04 · Owner 确定，按审计修订
> 仓库建好后放在仓库根目录，并在 AGENTS.md 第 1 节引用。Claude 和 Codex 都必须遵守。
> 本文只适用于 Shotviva，和 Owner 全局规则里 Graylum 的协作约定冲突时，以本文为准。

## 1. 角色

- **Owner**：定方向、拍板、批准合并和生产操作。
- **总控**：负责规划、审计、任务拆分与派发、合并前审查，维护本目录下的全部规范文件。默认由 Claude 担任，模式 3 下由 Codex 担任。
- **执行方**：按任务卡写代码、跑测试、提 PR。

## 2. 四种协作模式

| 模式 | 口令 | Claude 负责 | Codex 负责 |
|---|---|---|---|
| **1 双开** | 「切换协作模式 1」 | 总控（规划、审计、派活）+ 前端开发 | 后端、数据库、计费、支付等其余开发 + **所有浏览器验收** |
| **2 Claude 全包** | 「切换协作模式 2」 | 全部工作，包括浏览器验收（Codex 没额度时） | 无 |
| **3 Codex 全包** | 「切换协作模式 3」 | 无（Claude 没额度时） | 接管总控和全部工作 |
| **4 Claude 主做** | 「切换协作模式 4」 | 总控 + 全部开发 | **只负责浏览器验收** |

规则：

- Owner 说出口令即刻生效。总控要回复确认当前模式，并把模式和切换时间写进下面第 6 节的记录。
- **开发期的默认模式是 4**（Owner 2026-11-04 指定）。Owner 没有另外指定时按模式 4 执行，模式 1 作为可选。
- 谁「没额度」由 Owner 判定并下口令，Agent 不自行切换。
- 切换时进行中的任务不中断：已派出的任务卡由原执行方做完当前 PR；新任务按新模式派发。若接手方要接一个做了一半的任务，先在任务卡里写清交接进度，再接手。
- 模式 3 下，Codex 按本目录规范担任总控。Claude 恢复额度、Owner 切回其他模式后，Codex 要先交回进行中任务的状态，再由 Claude 接回总控。

## 2.1 总控窗口与开发窗口（Claude 一侧）

- **总控窗口只做审计、规划、派发任务和审查 PR，不直接写业务代码。**
- 每个开发任务都由总控新开一个 Claude 会话（开发窗口）执行，一个窗口对应一张任务卡。
- 开发窗口做完后向总控窗口汇报：做了什么、PR 链接、测试结果、遗留问题。总控核对 PR 和结果后再告诉 Owner。
- PR 被打回时，修改回到原开发窗口做；原窗口已关闭的，总控新开窗口，并在任务卡写明「续做」和上次停在哪里。总控不自己动手改 PR。
- 能并行的任务开多个开发窗口同时做，但两个窗口不准改同一批文件；需要隔离的放进各自的 git worktree。
- 需要 Codex 浏览器验收的，由总控在 PR 上发 `Validation handoff`，并告诉 Owner 让 Codex 去执行。

## 3. 任务卡

总控派活用 GitHub Issue 当任务卡，标题前缀写执行方，例如 `[Claude] 生成工作台`。仓库建立之前，任务卡写在 `规范/TASKS.md`，建仓后迁到 Issue。任务卡必须写清：

1. **目标**：做完之后什么样
2. **范围**：要动哪些目录和文件，明确不许动的地方
3. **依据**：直接摘抄本任务要遵守的规范条文，不只写章节号。开发窗口按卡执行，有疑问时才回去读整份规范
4. **验收标准**：可以逐条打勾，包括必须带的测试
5. **依赖**：要等哪张任务卡先完成

拆卡按功能竖切，不按前端、后端横切：同一个功能的前后端是一张卡、一个开发窗口、一个 PR。只有两部分真能各自独立合并时才拆成两张卡，这时接口定义（类型、路径、错误码）由总控先写进任务卡。

## 4. PR 与验收

- 执行方提 PR，PR 描述关联任务卡，写清改了什么、怎么验证。
- 总控审查 PR：对照任务卡和规范，不合格就打回并写清原因。
- 涉及页面或流程变化的 PR，需要浏览器验收。按当前模式由负责验收的一方执行（模式 1、4：Codex；模式 2：Claude；模式 3：Codex）：
  1. 总控在 PR 上发一条 `Validation handoff` 评论，对应当前提交：预览地址、测试账号的引用（不写密码）、带预期结果的编号步骤、通过和不通过的标准、不在本次范围内的内容。
  2. 验收方把每一步的实际结果写回 PR。
  3. 不通过：执行方在原分支修复。有新提交时，总控发新的 handoff，并说明是否需要重新验收。
- 遇到需要登录或人机验证的步骤，验收方停下请 Owner 处理。
- 合并前必须满足：CI 全过、总控审查通过、需要验收的已验收通过。合并由 Owner 批准。

## 5. 不管哪种模式都不变的

- 两个执行方不同时改同一批文件。
- 规范文件只有总控能改，执行方发现规范有问题就在任务卡里提出来。仓库建好后，规范改动单独开 `[spec]` PR，模式切换回来时接手方看这些 PR 就知道规范改了什么。
- 生产环境操作、改价格、加第三方服务，按 AGENTS.md 第 10 节先问 Owner。Owner 批准后，生产环境的数据库迁移和部署由总控执行（或由总控派给开发窗口执行）。
- 不在聊天里、PR 里、任务卡里写任何密码或密钥。
